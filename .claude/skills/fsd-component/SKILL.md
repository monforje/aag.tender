# Новый UI в FSD-проекте

Каркас этого проекта (топбар, рейл, флайаут, сайдбар, дерево, обвязка
страницы) перенесён из ClickUp-шелла с пиксельной точностью; поверх него
растут продуктовые экраны, у которых эталона нет. Отсюда два приоритета:
**не плодить копии** уже существующих рецептов и **не менять пиксели каркаса**
там, где их никто не просил менять.

Важно знать заранее: **файла эталона (`reference/index.html`) в рабочей копии
НЕТ** — папка удалена. Численно сверить правку не с чем, единственный след
эталона — `DESIGN-NOTES.md`. Тем более осторожно с числами каркаса.

Порядок работы: найти существующее → выбрать слой → создать файлы → написать
JSDoc → обновить реестр → проверить.

## 1. Сначала найти существующее

Самая частая ошибка в этом коде исторически — сделать седьмую копию того, что
уже есть. Аудит находил по 6 копий кнопки-иконки и по 3 копии аватара, и все
они отличались случайными числами, а не смыслом.

Прежде чем создавать, прочитай `COMPONENTS.md` и сверься с таблицей:

| Хочется сделать | Возьми готовое |
|---|---|
| Квадратную кнопку с иконкой | `IconButton` (варианты topbar / panel / page / rail; флаг `active` — «включено») |
| Кнопку с текстом в панели или полосе | `Button` (`primary` — одна на панель, `secondary` — все остальные; флаг `on`) |
| Тёмную кнопку в шапке СТРАНИЦЫ | `ChipButton` (28px, из эталона) — но только там; в панели это `Button variant="primary"` |
| Цветную плашку статуса | `Badge` (`tone` + `icon`); тон и глиф берутся из доменной таблицы, а не выбираются на месте |
| Кружок с буквой, инициал | `Avatar` (варианты workspace / user / tree) |
| Число рядом с пунктом | `Counter` (`muted` — если это количество, а не уведомление) |
| Строку выпадающего меню | `MenuItem`; если выбирают несколько подряд — `MenuCheckItem` + `Dropdown closeOnSelect={false}` |
| Панель внутри меню с кнопками внизу | `MenuPanel` (подвал «Очистить \| Готово» уже там) |
| Выпадающее меню | `Dropdown` + `DropdownGroup`, если их несколько в одной полосе |
| Модальное окно | `Modal` + `modalPart` (открытость — проп `open`, не `ref.showModal()`) |
| Панель, падающую из кнопки и вылезающую за прокручиваемый контейнер | `Popover` (привязка правым краем, откидывание вверх — уже там) |
| Поле поиска, сужающее список | `SearchInput` (`capsule` в полосе, `field` в панели) |
| Поиск по всему приложению | `SearchTrigger` — это КНОПКА, открывающая модалку |
| Таблицу данных | `Table` + `tableCell` (модификаторы ячеек отдаёт сам компонент); `layout="fixed"` — когда колонки СРАВНИВАЮТ и ширина обязана быть равной |
| Фильтр по нескольким полям с кучей значений | `FacetFilter` |
| Значение, которое правят на месте | `InlineInput` — в покое как текст, заливка по наведению. Поверхность общая, `.inline-edit` в `global.css` |
| Выбор ОДНОЙ даты | `DatePicker` — кнопка со значением + поповер с календарём |
| Выбор периода | `RangeCalendar` — поля ввода + два месяца, границы правятся по отдельности |
| Сетку месяца саму по себе | `CalendarMonth` из `shared/ui/Calendar` — её уже делят оба календаря, третьей копии быть не должно |
| Прокручиваемую область | `ScrollArea` + `useScrolled` для тени липкой шапки |
| Строку списка/дерева | `TreeRow`; для узла с детьми — `NestedTreeNode`; целое дерево — `Tree` |
| Шапку экрана, заголовок, действия | `PageHeader` / `PageTitle` / `PageActions` |
| Вкладки среза данных внутри экрана | `SecondaryHeader` + `PageHeader withSecondary` |
| Заглушку пустого экрана | `ScreenPlaceholder` |
| Текст для скринридеров | `VisuallyHidden` |
| Дату привести к сравнимому виду или разобрать введённую | `shared/lib/date`: `isoLocal`, `dmyToIso`, `isoToDmy`, `parseDmy`, `shortDate`, `startOfMonth` |
| Переключить значение в мультивыборе | `shared/lib/toggle` |

Если нужное почти совпадает — **добавь вариант в существующий компонент**, а не
новый файл. Вариант описывает поверхность или роль («panel», «user»), а не
набор чисел: свободные `size`+`radius` в этом проекте разъезжаются с эталоном,
потому что у оригинала радиусы не следуют размеру (28px→7px, 32px→6px,
32px на рейле→8px).

Создавать новое стоит, когда: другая семантика, другой контракт пропсов или
принципиально другое поведение. Тогда — дальше по списку.

## 2. Выбрать слой

Решающий вопрос: **может ли этот компонент жить в другом приложении, если
переименовать только импорты?** Если да — `shared`. Если он знает про задачи,
воркспейсы, разделы — не `shared`.

| Слой | Что туда кладут | Признак |
|---|---|---|
| `shared/ui/<Name>/` | Примитивы: кнопки, аватары, меню, области прокрутки | Не знает ни одного доменного слова |
| `entities/<name>/` | Данные домена + их представление | Знает про «раздел», «задачу», «пользователя» |
| `features/<name>/` | Сценарий со своим состоянием и таймингами | Есть поведение, которое можно включить и выключить |
| `widgets/<name>/` | Композиция под конкретное место каркаса | Существует в единственном экземпляре на экране |
| `pages/<name>/` | Экран под маршрутом | Ему соответствует адрес |

Правило зависимостей — только вниз: `pages → widgets → features → entities →
shared`. Виджет может импортировать фичу, фича виджет — нет. Если тянет
нарушить, значит слой выбран неверно: обычно спасает вынос общей части в
`shared` с передачей ДАННЫХ пропом. Так сделаны две последние пары:
`shared/ui/Tree` рисует дерево, а `entities/section` только отдаёт ему
`TreeItem[]`; `shared/ui/FacetFilter` рисует окно фильтров, а
`entities/tender` отдаёт ему `FACETS` — про портфели и виды работ компонент
не знает.

## 3. Создать файлы

Быстрый путь — скрипт, он разложит файлы и подставит шаблоны:

```bash
python3 .claude/skills/fsd-component/scripts/scaffold.py shared/ui Tooltip
python3 .claude/skills/fsd-component/scripts/scaffold.py widgets inspector
```

Что получается:

```
shared/ui/Tooltip/
├── Tooltip.tsx          — компонент с JSDoc-шапкой
├── Tooltip.module.css   — стили
└── index.ts             — публичный API слайса
```

Для `widgets`, `features`, `pages`, `entities` добавляется `ui/` и `model/`.

**Импортировать только через публичную точку**: `@/shared/ui/Tooltip`, никогда
`@/shared/ui/Tooltip/Tooltip`. Глубоких импортов в проекте нет ни одного, и это
стоит сохранить — иначе перестановка файла ломает потребителей.

## 4. Написать JSDoc

Шапка компонента — не украшение: по ней следующий человек решает, брать этот
компонент или другой. Без раздела «НЕ ДЛЯ» через месяц появится дубликат.

```tsx
/**
 * Одна строка: что это.
 *
 * КОГДА:  в каких случаях брать именно его
 * НЕ ДЛЯ: когда взять другой — с прямой ссылкой на него
 *
 * UX:     что происходит на hover/focus/active, что анимируется и что
 *         намеренно НЕ анимируется
 * A11Y:   роль, обязательные подписи, поведение с клавиатуры
 *
 * @example
 * <Tooltip text="Скопировано">{children}</Tooltip>
 */
```

Пиши «почему», а не только «как». Формулировка «активность кодируется фоном, а
не жирным шрифтом — одно состояние, один канал» переживает рефакторинг;
формулировка «здесь background .06» — нет.

## 5. Стили: чего здесь легко не заметить

### Поверхности тоже берутся из общего

Кроме токенов и рецептов, в `global.css` живут ГЛОБАЛЬНЫЕ, нехэшированные
классы-утилиты — для того, что делят элементы разных типов из разных модулей и
что не выражается компонентом:

- `.visually-hidden` — текст только для скринридеров (обёртка `VisuallyHidden`);
- `.inline-edit` (раздел 1-b) — поверхность значения, которое правят на месте:
  в покое как текст, заливка по наведению, белая подложка с кольцом по фокусу,
  заливка растёт наружу отрицательным margin. Её делят `<InlineInput>` и кнопка
  `<DatePicker>` — поле и кнопка, то есть селектором одного модуля их не
  накрыть.

Заводя такой класс, не клади в него `display` и `width`: у разнотипных
потребителей они разные, и как только утилиту приходится перебивать из модуля,
результат начинает зависеть от порядка файлов в сборке.

### Состояния берутся из шкалы

В `src/app/styles/global.css` лежат токены и **каталог из десяти рецептов** —
закрытый список того, как элемент отвечает на курсор и фокус. Новые значения
альфы не изобретают; ступень выбирают по двум правилам:

- `--cu-state-hover-subtle` (.05) — крупная поверхность: строка списка, пункт
  меню, текстовая кнопка. Большой площади хватает слабой заливки;
- `--cu-state-hover` (.06) — компактный контрол 22–32px и текущее состояние;
- `--cu-state-hover-strong` (.09) — контрол, у которого в покое уже есть
  заливка: поверх собственного фона слабая не читается;
- `--cu-state-ring` — белая капсула на светлом фоне, заливать нечем;
- `--cu-focus-ring` — фокус с клавиатуры.

Если ни один рецепт не подходит — это повод обсудить одиннадцатый и записать
его в каталог, а не написать свой в модуле. Так туда попал рецепт 10
(раскрытие подписи под курсором): у него в каталоге прописаны три условия
применимости, потому что в общем случае менять размер под курсором нельзя.

**Смысловой цвет — тоже токен.** Статусы и прочие «идёт / готово / отменено»
берут `--cu-tone-*` из того же `global.css`: сам цвет, `-ink` для текста
поверх заливки и `-fill` для заливки. Тип `Tone` экспортирует `shared/ui/Badge`
— доменные таблицы статусов типизируются им, чтобы не завести вторую палитру.

### Reset уже всё сделал за кнопку

`global.css` даёт всем `button` `background:none; border:0; padding:0;
font:inherit; cursor:pointer`. Повторять это в модуле не нужно — лишние
строки создают впечатление, что где-то иначе.

### Класс-модификатор проигрывает по специфичности, если базовое правило с тегом

`.table td` — это (0,1,1), одиночный класс — (0,1,0). Поэтому правило вида
«эта колонка вправо» обязано писаться `.table td.cell--numeric`, иначе оно
молча не применится. В этом проекте так дважды ломались колонки дат и
паддинг строки «ничего не найдено».

### Селектор не пересекает границу CSS-модуля

Классы хэшируются помодульно, поэтому `.parent .child`, где `.parent` объявлен
в одном модуле, а `.child` в другом, **не совпадает ни с чем**. Правило молча
перестаёт работать — ошибок не будет ни в сборке, ни в типах. В этом проекте
так дважды ломались тень липкой шапки и проявление контролов сайдбара.

Три рабочих выхода, в порядке предпочтения:

1. **Состояние на самом элементе.** Компонент принимает проп и вешает свой
   модификатор: `cx(s.header, scrolled && s.headerScrolled)`. Так и правильнее
   по смыслу — тень принадлежит шапке, а не панели.
2. **CSS-переменная как мост.** Кастомные свойства наследуются по DOM и хэшей
   не имеют: предок на `:hover` переопределяет `--x-opacity`, потомок в другом
   модуле её читает. Так сделано проявление `.sidebar-final__actions`.
3. **Один модуль на связанное семейство.** Если элементы сцеплены `:has()`-
   правилами (шапка сайдбара: фокус в поиске схлопывает заголовок), держи их
   стили в одном модуле, даже если компоненты разные. Границы компонентов и
   границы стилей не обязаны совпадать.

4. **Класс отдаёт наружу сам модуль.** Если правило обязано быть сцеплено с
   собственным предком (`.table td.cell--numeric`), класс не может прийти
   снаружи — компонент публикует его сам: `tableCell` у `Table`,
   `searchSecondaryIconClass` у `SearchTrigger`.

Чужой `.icon`, `.counter` и подобные адресовать нельзя — передавай класс
пропом: `<Icon className={s.rowIcon} />`.

### Проверка

```bash
python3 .claude/skills/fsd-component/scripts/check_css_modules.py
```

Скрипт находит классы, объявленные в модуле, но не применённые ни одним его
потребителем, — это либо мёртвое правило, либо селектор, ушедший в чужой
модуль. Норма — ноль.

## 6. Обновить COMPONENTS.md

Реестр существует ровно затем, чтобы следующий человек нашёл готовое и не
сделал копию. Компонент, которого в нём нет, будет продублирован.

Добавь строку в таблицу нужного слоя:

```markdown
| `Tooltip` | Подсказка по наведению | Пояснение к контролу, который не объясняет себя сам |
```

Если появился новый токен состояния, новый семантический тон или новый рецепт
взаимодействия — допиши его в раздел «Состояния» там же и в каталог в
`global.css`. Если компонент закрыл или создал долг — правь список «Что
осталось нерешённым» в конце `COMPONENTS.md`: он там не для красоты, по нему
решают, что делать дальше.

## 7. Проверить

```bash
bunx tsc --noEmit && bun run build
```

Плюс детектор осиротевших классов из шага 5.

Дальше — живая страница. **Эталона в рабочей копии нет**, сверять «две
страницы рядом» не с чем, поэтому проверка стала прямой: открыть приложение и
снять с него числа, ожидаемые из `DESIGN-NOTES.md`. Минимум для любого экрана
в `<main>`: заголовок страницы, первая вкладка и первая колонка контента лежат
на одной вертикали в 12px от левого края `<main>`.

Две ловушки, на которых легко получить ложный результат:

1. **Выключить переходы** перед снятием стилей:
   `*{transition:none!important;animation:none!important}`. Если панель
   браузера скрыта, страница не композитит кадры, анимации зависают в
   состоянии `running`, и вместо конечных значений меряются стартовые: у
   только что открытого меню вы увидите `opacity: 0` и решите, что оно
   сломано. По той же причине не работают `requestAnimationFrame` и нативные
   события `scroll`.
2. **Состояния по наведению численная сверка не видит.** Все дефекты,
   найденные в этом проекте после рефакторингов, были именно в hover — в
   покое всё совпадало идеально. Наводите курсор (`hover` в браузерных
   инструментах) и читайте вычисленный фон, либо сравнивайте сами
   CSS-правила.

Отдельно: **клик из скрипта не заменяет клик пользователя**. Два `.click()`
подряд в одном тике React не перерисует между ними, и компонент со
состоянием (диапазон в календаре, мультивыбор) отработает по устаревшим
пропсам — выглядит как баг, которого нет.
