# Аудит фильтров, сортировок и пометок таблицы сравнения КП

Разбор двух макетов из `filter_audit/`. Цель — вытащить **смысловые data
pipelines**: что является входом, что вычисляется, по какой формуле и на что
влияет. Вёрстка, цвета, расположение контролов **сознательно не разбираются** —
переносить их не планируется.

Все числовые утверждения ниже проверяются скриптом:

```bash
bun filter_audit/probe.js
```

Он читает данные прямо из макета, а не копирует их: если макет поправят,
расхождение с этим текстом всплывёт падением, а не тихо.

## 0. Что за файлы и как они соотносятся (история)

| | `Сравнение КП.dc.html` | `tender-comparison-full.html` |
|---|---|---|
| дата | 18.08, 925 строк | 19.08, 1114 строк |
| формат | DC-компонент (`class Component extends DCLogic`, шаблон + `renderVals()`) | standalone HTML + императивный `renderAll()` |
| охват | шире: две вкладки **Сравнение / Решение**, редактируемая шапка тендера, привязка к статье бюджета с проверкой лимита, карточки решения по подрядчику, протокол | уже: только сравнение + панель анализа |
| фильтров | 4 | 5 (добавлен `above_median`) |

**Ядро данных у обоих идентично**: те же 20 позиций, 3 подрядчика, 4 раздела,
те же три пресета с теми же значениями, те же пять сценариев анализа и те же
тексты инсайтов. То есть это две подачи одной модели, а не две модели.

### Расхождения в поведении (это и есть «история» изменений)

1. **Момент фильтрации.** `full` фильтрует **визуально**: строка рендерится
   всегда и прячется классом `is-filtered-out { display:none }`. `dc` фильтрует
   **фактически**: `list = ITEMS.filter(matches)` до сборки блоков.
   Следствие, которое переносить нельзя: в `full` **подытоги разделов считаются
   по всем строкам, включая скрытые** — на экране три строки, а «Итого · Материалы»
   учитывает пять. В `dc` подытог отвечает фильтру. Правильно — `dc`.
2. **Снятые позиции.** `full`: `ITEMS.filter(i => !i.removed || filters.length === 0)`
   — снятая позиция исчезает при включении *любого* фильтра, даже никак с ней не
   связанного. `dc` такого правила не имеет. Правило в `full` — костыль: снятая
   позиция и так не проходит ни один из пяти фильтров.
3. **Пятый фильтр `above_median`** появился только в `full` и сломан (см. §4.5).
   В `dc` его нет — судя по всему, отказались осознанно.
4. **Единственный числовой порог во всём коде** — в `dc`: цифра в ячейке краснеет
   при `mainMetric === 'deviation' && cell.deviation > 5`. Порог 5 %,
   **несимметричный** (−8,5 % остаётся чёрным). В `full` этого нет.
5. **Итоговая строка.** `dc` добавляет к колонке подрядчика «лучшее предложение» /
   «+X к лучшему» (`best = min(total)`). `full` показывает голые суммы.
6. **Признак «пресет изменён».** `full` сравнивает `mainMetric`, `rowView`,
   `filters` и `extraMetrics`; `dc` — первые три. В `dc` смена доп. показателя
   не помечает пресет изменённым.
7. **Мусор в `full`**: `state.hiddenSuppliers` заведён, читается в
   `visibleSuppliers()`, но не пишется никем — мёртвая ветка. И магическое число
   `12156000` в подписи «% среза» (см. §3.2).

### История внутри модели данных

Помимо истории файлов, в самой модели есть три слоя «изменений», которые и
имелись в виду под «изменениями таблицы» — разобраны в §5:
версия КП у подрядчика (`version` + `<select>`), правки сметы
(`removed` / `corrected` + `qtyOrig`), отказ подрядчика по строке (`declined`).
Плюс заглушка сохранённых прогонов анализа — `history` в `full`
(`12.07 · Что важно`, `11.07 · Торги`), ни к чему не подключённая.

## 1. Пресеты: Обзор / Торги / Аномалии

### Смысл
Не фильтр и не сортировка, а **сохранённая комбинация всех остальных
контролов** — «под каким углом смотрим на этот же срез». Один клик = ответ на
один вопрос: *что вообще предложили* → *где ещё можно отжать* → *где врут или
ошиблись*.

### Формула
Пресет — чистое присваивание четырёх полей состояния, без своей логики:

```js
PRESETS = {
  overview:  { mainMetric: 'price',     extraMetrics: [],        rowView: 'sections',  filters: [] },
  bidding:   { mainMetric: 'potential', extraMetrics: ['price'], rowView: 'potential', filters: ['has_potential'] },
  anomalies: { mainMetric: 'deviation', extraMetrics: ['price'], rowView: 'weight',    filters: ['anomalies'] },
}
```

`applyPreset(id)` / `setPreset(id)` перезаписывают `mainMetric`, `extraMetrics`,
`rowView`, `filters` целиком. Обратной связи нет: любое ручное изменение любого
из четырёх полей не переключает пресет, а поднимает флаг:

```js
modified = mainMetric !== base.mainMetric
        || rowView    !== base.rowView
        || sorted(filters)      != sorted(base.filters)
        || sorted(extraMetrics) != sorted(base.extraMetrics)   // только в full
```

Флаг рисует «ИЗМЕНЁН · СБРОС»; сброс — это `setPreset(текущий)`, то есть
повторное применение той же тройки.

### На что влияет
На всё сразу: показатель в ячейке, набор подстрочных показателей, порядок и
группировку строк, активные фильтры. Пресет — единственная точка, где эти
четыре независимых оси связаны.

### Сцепка со сценариями анализа
Панель анализа умеет дёргать пресет обратно — односторонний мост:

```js
scenario 'bidding'   → setPreset('bidding')
scenario 'anomalies' → setPreset('anomalies')
остальные сценарии   → таблицу не трогают
```

То есть «Точки торгов» и «Риски и аномалии» в панели ИИ — это те же пресеты,
названные иначе. При переносе это должна быть одна сущность, а не две.

### Что ломается при переносе
- `bidding` включает `has_potential`, который отсекает **1 позицию из 20**
  (проверено). Пресет «Торги» практически ничего не фильтрует — вся его
  полезность в сортировке по потенциалу.
- `bidding` и `anomalies` ставят `rowView` ≠ `sections`, а в этом режиме
  **разделы и подытоги пропадают полностью**. Смена пресета молча уничтожает
  структуру сметы — и это не опция, а побочный эффект.

## 2. Показатель: Цена / Отклонение / Потенциал

### Смысл
Ячейка на пересечении «позиция × подрядчик» несёт три числа. Переключатель
выбирает, **какое из них главное** (крупным), остальные из `extraMetrics`
уходят подстрочником. Это не фильтр: набор строк не меняется, меняется
прочтение.

```js
shownMetrics() = unique([mainMetric, ...extraMetrics]).slice(0, 3)
metricValue(m, cell):
  !cell || cell.missing → '—'
  m === 'deviation'     → (n>0?'+':'') + n.toFixed(1) + '%'
  m === 'potential'     → potential ? money(potential) : '—'
  иначе                 → money(price)
```

### 2.1 Цена
Сумма по позиции в рублях. **Вход.**

Внимание при интеграции: в макете `price` — это **сумма по строке**
(цена × объём), а в текущем коде `entities/tender/model/comparison.ts` цена
хранится **за единицу**, и это решение задокументировано и правильное. Значит
`deviation` и `potential`, выраженные в рублях строки, при переносе обязаны
либо пересчитываться в удельные, либо явно объявляться «величина по строке».

### 2.2 Отклонение (`deviation`)
Процент, **вход**, не вычисляется в макете ни разу.

Что удалось восстановить обратным счётом (`probe.js`, п. 5): если подставить
`base = price / (1 + deviation/100)`, то **внутри строки база сходится по всем
ячейкам с точностью ≤ 0,30 %**. То есть у каждой строки есть ровно одна
базовая цена, от которой считалось отклонение.

Но эта база **не равна** ни минимуму, ни среднему, ни медиане цен строки: с
любым из трёх она совпадает только в 7 строках из 20. Примеры:

| строка | цены | база | что это |
|---|---|---|---|
| #1 Бетон | 2 184 / 2 310 / 2 268 тыс. | ≈ 2 256 тыс. | ≈ среднее (2 254) |
| #2 Арматура | 4 472 / 4 386 / 4 120 тыс. | ≈ 4 397 тыс. | ≈ медиана (4 386), но мимо на 0,24 % |
| #3 Щебень | 324 / 342 / 331 тыс. | ≈ 324 тыс. | = минимум |
| #7 Фундамент | 5 184 / 5 460 / 5 292 тыс. | ≈ 5 462 тыс. | = максимум |
| #18 Прогрев | 504 / 462 тыс. | ≈ 450 тыс. | **ниже обеих цен** |

**Вывод для пайплайна:** отклонение считается от внешней эталонной цены строки
(сметная / бюджетная / прошлая закупка), которой в макете просто нет. Это
самый важный пробел контракта: без явно названной базы «Отклонение» и
«Аномалии» не воспроизводятся, а подобрать её по ценам КП нельзя — макет это
доказывает.

### 2.3 Потенциал (`potential`)
Рубли, **вход**. Смысл — «сколько ещё можно отжать по этой ячейке».

Проверено: `potential = price − min(строки)` выполняется лишь в 2 строках из
20. То есть это **не переплата относительно лучшего**. Разбор данных показывает,
что потенциал задавался как круглая скидка на единицу × объём
(`potential / qty` = 200, 100, 2000, 50, 5, 25, 650, 500, 20…), причём в
датасете **смешаны две несовместимые трактовки**:

- **(а) запас торга у дешёвого** — строки #1, 6, 7, 8, 10, 12, 13, 14, 15, 16,
  17, 19, 20: потенциал стоит у подрядчика с минимальной ценой, у остальных 0.
  Читается как «даже лучший ещё подвинется».
- **(б) переплата у дорогого** — строки #3, 5: потенциал у тех, кто дороже, и
  численно равен разнице с минимумом. Читается ровно наоборот.

Одну из двух трактовок нужно выбрать до интеграции — от неё зависит и
сортировка «По потенциалу», и весь пресет «Торги».

### Агрегаты потенциала, которые уже используются
```js
maxPot(item)  = max по подрядчикам        // ключ сортировки rowView='potential'
Σ maxPot      = 1 194 200 ₽               // док: «потенциал торгов по срезу»
Σ potential по колонке                     // карточка решения: 891 400 / 121 100 / 444 520 ₽
```
`Σ maxPot` складывает максимумы **разных подрядчиков** в одно число — величина
не соответствует ни одному достижимому сценарию закупки. Если такой показатель
нужен, его надо определять относительно выбранного подрядчика.

### На что влияет выбор показателя, кроме текста в ячейке
Скрытая сцепка, которую легко потерять: **зелёная подсветка минимума и бейдж
`min` живут только при `mainMetric === 'price'`**

```js
isMin = cell.isMin && mainMetric === 'price'
```

Переключение на «Отклонение» или «Потенциал» гасит всю разметку минимумов.
Логика: «min» — утверждение про цену, и на колонке процентов оно означало бы
другое. Решение правильное, переносить.

## 3. Вид строк: По разделам / По весу / По потенциалу

### Смысл
Порядок и **наличие группировки**. Это не сортировка колонки — это выбор оси, по
которой смета вообще выкладывается.

### 3.1 Формулы
```js
list = ITEMS (в full — за вычетом снятых, если есть хоть один фильтр)

rowView === 'weight'    → sort by weight(item)  desc,  плоский список
rowView === 'potential' → sort by maxPot(item)  desc,  плоский список
rowView === 'sections'  → исходный порядок, разбитый по SECTIONS

weight(item) = max(цены подрядчиков по строке)      // не среднее и не минимум
maxPot(item) = max(потенциалы подрядчиков по строке)
```

`weight` берёт **максимум**, то есть «во сколько эта позиция обойдётся в худшем
случае» — как оценка риска, а не факта. Для «на что влияет наша смета» логичнее
был бы минимум или цена выбранного подрядчика; это осознанный выбор, но его
надо подтвердить, а не унаследовать молча.

### 3.2 «% среза» — сломанный показатель
Только в `full`, только при `rowView === 'weight'`, подписью в ячейке:

```js
(weight(item) / 12156000 * 100).toFixed(1) + '% среза'
```

`12 156 000` — захардкоженный итог подрядчика №2. База среза по этой же формуле
(`Σ weight`) равна `19 914 600`. Сумма всех «% среза» = **164 %**. Показатель
нужно либо считать от `Σ weight`, либо от итога выбранного подрядчика, но
называть иначе.

### 3.3 Только `sections` даёт итоги
```js
sections: [заголовок раздела] [строки] [Итого · раздел]  — подытог = Σ price по колонке
weight / potential: только строки, ни заголовков, ни подытогов, ни группировки
```

Итого по срезу (tfoot) при этом **всегда** берётся из `SUPPLIERS[].total` и не
реагирует ни на фильтры, ни на вид строк.

### 3.4 Итоги не сходятся — данные несогласованы
| подрядчик | заявленный `total` | Σ цен по ячейкам |
|---|---|---|
| МетСнаб | 11 840 000 | 18 726 200 |
| ИнженерГрупп | 12 156 000 | 19 462 300 |
| СтройМонтаж | 11 980 000 | 19 227 100 |

Расхождение в 1,6 раза системное, а не опечатка: 20 позиций в таблице —
**выборка сметы**, а `total` относится ко всей смете. Пока это так, подытог
раздела и итог по срезу — числа из разных вселенных, и складывать их на одном
экране нельзя. В `comparison.ts` эта проблема уже решена правильно: `sumOf()`
считает и итог, и подытог из одних строк.

## 4. Изменения таблицы — три независимых слоя

Ни один не влияет на фильтры и сортировки; всё это разметка «что поменялось с
момента публикации».

1. **Версия КП подрядчика.** `supplier.version` (`КП v2 · 12.07`) плюс
   `<select>` в шапке колонки со списком версий. Смысл — подменить весь столбец
   другой редакцией предложения и пересчитать сравнение. В макете переключение
   ничего не делает. В шапке тендера отдельно живёт `ФКП v3 · 14.07.2026` —
   финальная версия сметы.
2. **Правки сметы.** `removed` (строка снята, зачёркнута, ячейки схлопнуты в «—»)
   и `corrected` + `qtyOrig` (объём изменён, показываются оба:
   `1200 → 1260`). Это дифф против исходной сметы, живущий прямо в строке.
3. **Отказ подрядчика.** `declined[supplierId]` — подрядчик сознательно не берёт
   объём. Отличается от `missing` («нет цены»): отказ — решение, отсутствие —
   пробел. Это различие в `comparison.ts` уже отражено (отсутствие ключа ≠ ноль),
   но третьего состояния «отказ» там пока нет.

Есть и четвёртая заглушка: `history` в `full` — чипы сохранённых прогонов
анализа (`12.07 · Что важно`), ни с чем не связанные. Смысл, который туда
закладывался: **анализ версионируется вместе с раундом торгов**.

## 5. Контракт данных: что вход, что вычисляется

Итог аудита в одну таблицу. Слева — то, что обязан отдать бэкенд, справа — то,
что фронт считает сам.

### Обязаны прийти извне
| поле | уровень | почему нельзя вывести |
|---|---|---|
| `price` | ячейка | исходные данные КП |
| `deviation` | ячейка | база отклонения — внешняя эталонная цена, из цен КП не выводится (§2.2) |
| `potential` | ячейка | не равен переплате, задаётся торговой оценкой (§2.3) |
| `anomaly` (+ **причина**) | ячейка | ни один порог по отклонению не воспроизводит разметку (§4.3) |
| `missing` / `declined` | ячейка | разные состояния, оба — факт о КП (§5) |
| `isKey` | строка | решение закупщика (либо правило «топ по весу», §4.1) |
| `removed`, `corrected`, `qtyOrig` | строка | дифф против сметы (§5) |
| `coverage`, `version` | подрядчик | факт о КП |
| **эталонная цена строки** | строка | **отсутствует в макете, но нужна** — без неё нет ни отклонения, ни аномалий |

### Считается на фронте
```js
spreadPct(item) = (max − min) / min * 100          // есть в comparison.ts как spread()
spreadTag       = порог поверх spreadPct           // ← нужно ввести, в макете это вход
isMin           = min среди НЕаномальных цен       // ← формализовать, в макете это вход
weight(item)    = max цен по строке
maxPot(item)    = max потенциалов по строке
sum(колонка)    = Σ price                          // есть как sumOf()
sum(раздел)     = Σ price по строкам раздела       // есть как groupSum()
rank            = порядок по сумме                 // есть как rankBids(), но см. ниже
счётчики        = count по предикатам разметки
```

### Что в текущем коде уже решено лучше макета
`src/entities/tender/model/comparison.ts` — не выбрасывать при интеграции:

- **цена за единицу, а не сумма строки** — сумма выводится, объём общий; макет
  хранит суммы и тем самым допускает рассогласование с объёмом;
- **отсутствие ключа = позиция не закрыта, а не ноль** — макет местами кладёт
  `price: 0` с флагом `missing`;
- **`spread()` возвращает `null` при <2 цен** — макет отдаёт `«—»` строкой;
- **`rankBids()` сортирует двухключево: сначала полнота КП, потом сумма** —
  макет ранжирует чисто по `total` и потому в `dc` объявляет «лучшим
  предложением» просто минимальную сумму, не глядя на 88 % покрытия. Это прямое
  противоречие; правы — `rankBids`;
- **итог и подытог считаются из одних строк** — в макете они из разных
  источников и не сходятся в 1,6 раза (§3.4).

## 7. Что перенести, что переделать, что выбросить

**Перенести как есть (смысл верный):**
- пресет = именованный набор {показатель, доп. показатели, вид строк, фильтры} + флаг «изменён» и сброс;
- три показателя в ячейке, главный крупно + подстрочник;
- гашение разметки минимумов вне режима «Цена»;
- «min» присуждается лучшей неаномальной цене;
- фильтры комбинируются по И, сброс одной кнопкой;
- три слоя изменений: версия КП, правка сметы, отказ;
- форма инсайта: тон `risk|trade|info` + якорь на строку + ссылка на правило.

**Переделать до переноса:**
- фильтровать **до** подсчёта подытогов (как в `dc`), иначе итоги врут;
- `spreadTag` вычислять из `spread()` по явному порогу, а не принимать полем;
- `has_potential` дополнить порогом, иначе фильтр — no-op;
- «% среза» считать от базы среза, а не от чужого итога;
- `Σ maxPot` либо привязать к выбранному подрядчику, либо не показывать;
- определить одну трактовку потенциала — запас торга ИЛИ переплата (§2.3);
- ввести эталонную цену строки как явное поле контракта.

**Выбросить:**
- фильтр «Выше медианы» в нынешнем виде (не медиана, зависит от порядка ★,
  пустит таблицу в ноль без избранного);
- правило «любой фильтр прячет снятые позиции»;
- мёртвый `hiddenSuppliers` и магическое `12156000`;
- заявленный `total` подрядчика как источник итога — считать из строк.

## Приложение. Дизайн-спека управления сравнением КП

Вёрстка макетов не переносится (см. преамбулу), но управление экраном где-то
должно жить. Ниже — зафиксированный дизайн контролов и таймингов; живое
превью со всеми формулами, попапами и иконками — `filter_audit/badges.html`
(открыть в браузере). Бейджи ячеек разобраны отдельно в `bages.md`, здесь —
полоса управления, слои таблицы и панель инсайтов.

### Д.1 Анатомия полосы: один сегмент, два дропдауна, один поповер

Ряд из пяти кнопок-фильтров — забор: пять равных прямоугольников без суммы,
без критериев, без места для нового предиката. Решение:

```
[ Обзор│Торги│Аномалии ]  Показатель: Цена ⌄   [↕] Строки: По разделам ⌄   [▽ Фильтры •N]
```

- **Пресеты — сегмент-контрол**, единственный кнопочный элемент полосы.
  Пресетов ровно три, они взаимоисключающие и переключаются часто — кнопки
  оправданы здесь и только здесь.
- **Показатель и Вид строк — тихие триггеры с меню**: подпись третичным,
  текущее значение medium, шеврон `alt-arrow-down`. Значение видно всегда —
  раскрывать полосу ради статуса не нужно. Нативный `<select>` запрещён:
  раскрытый список рисует ОС.
- **Предикаты — ОДИН триггер «Фильтры»** (иконка `filter`) с каунтером
  выбранных и поповером чек-листа. В пункте: точка тона (та же, что красит
  ячейки), название, справа — сколько строк предикат пропустит на текущих
  данных до применения этого же фильтра. Футер: «Сбросить всё» (`refresh`)
  disabled при пустом наборе и «Готово». Мультивыбор сериями — меню не
  закрывается по клику (`closeOnSelect={false}`).
- Активные предикаты НЕ выносятся чипами в полосу — это тот же забор.
  Список виден в поповере, на полосе живёт одно число.

### Д.2 Пресет — четыре оси и флаг «изменён»

Формула из §1 переносится буквально: пресет присваивает
`{mainMetric, extraMetrics, rowView, filters}` целиком. UI добавляет ровно
одну вещь, которой в макете не было: **чип «Изменён · Сброс»** рядом с
сегментом. Любое ручное движение по четырём осям уводит состояние от базы
пресета — молча терять это нельзя: пользователь должен видеть, что смотрит
не на «Обзор», а на его собственную нарезку. Чип = `modified` из §1,
кнопкой он делает одно действие — повторное применение текущего пресета.

Мост инсайтов сохраняется односторонним: сценарии «Точки торгов» и «Риски и
аномалии» — это пресеты `bidding` и `anomalies`, одна сущность под двумя
именами.

### Д.3 Показатель и формулы ячейки

`shownMetrics()` и `metricValue()` переносятся как есть (§2), с поправками
аудита:

- **`min` гаснет вне режима «Цена»** — `isMin && mainMetric === 'price'`
  (§2, решение правильное).
- **min присуждается лучшей НЕаномальной цене**, аномальная остаётся только
  в разбросе (§4.6).
- **`spreadPct` считается по всем ценам включая аномальные**, порог поверх
  вычисленного процента: `high ≥ 15 %`, `noticeable ≥ 7 %`; метка выводится
  из процента, не приходит рядом (§4.2). Шкала под процентом масштабируется
  как 25 % = вся шкала.
- **Отклонение в превью считается от медианы строки — это ЗАМЕНА, а не
  решение.** Аудит доказал (§2.2), что база отклонения — внешняя эталонная
  цена, которую из цен КП вывести нельзя. До появления поля в контракте
  медиана годится для демонстрации режима и ни для чего больше.
- Красная цифра при превышении допуска становится **симметричной**
  (`|deviation| > 5 %`): несимметричный порог `dc` (−8,5 % оставался
  чёрным) — дефект, а не правило (§0, п. 4).

### Д.4 Вид строк и итоги

- `weight = max(цен)` desc, `maxPot = max(потенциалов)` desc, плоские
  списки; `sections` — исходный порядок с заголовками разделов и подытогами
  (§3.1, §3.3).
- **Подытоги и итог считаются из одних видимых строк** — правило `dc`,
  визуальная фильтрация `full` врёт в подытогах (§0, п. 1).
- «% среза» в превью переименован в **«доля веса» и считается от
  `Σ weight` среза**, не от чужого итога подрядчика; сумма долей = 100 %
  (§3.2).

### Д.5 Попап ячейки: тайминги по NN/g

Попап — объяснение пометки («почему так»), живёт в нативном `<dialog>`:
таблица прокручивается внутри `overflow-x:auto`, и абсолютный div был бы
обрезан — top layer обходит это физически. Тайминги взяты из гайдлайна
NN/g «Timing Guidelines for Exposing Hidden Content» (0,1 с обратная связь /
0,3–0,5 с остановка курсора до показа / >0,5 с вне зоны до скрытия):

| параметр | значение | почему |
|---|---|---|
| обратная связь на наведение | сразу | подсветка строки уже есть — рецепт 1 каталога состояний |
| показ после остановки курсора | 350 мс | нижняя граница коридора 300–500 мс: проход по столбцу не хлопает попапами |
| переход между соседними ячейками | мгновенно, содержимое меняется на лету | Microsoft «reshow ≈ 0,1 с»: серия вопросов без ожидания |
| сокрытие после ухода курсора | 500 мс | мост курсора ячейка → панель; уход НА панель отменяет закрытие |
| скролл таблицы | закрыть немедленно | панель не должна «плыть» над чужой строкой |
| Escape / клик мимо / возврат фокуса | платформа (`<dialog>`) | закрывается через ту же анимацию |
| клавиатура | focus открывает, blur закрывает | то же объяснение без мыши |

Контент собирается из модели ячейки: тон success для минимума (глиф
`check-circle`), warning для аномалии (глиф `danger-triangle`) с причиной
первым блоком — контракт «аномалия приходит с причиной» (§4.3).

### Д.6 Инсайты

Контракт §4.7 переносится с тонами проекта: `risk → danger`,
`trade → success`, `info → info`; иконки соответственно `danger-triangle`,
`graph-up`, `info-circle`. Клик по карточке подсвечивает строку-якорь
заливкой `--cu-state-hover` на 2,4 с и подтягивает её в видимую область —
подсветка временная, потому что это ответ на вопрос, а не состояние данных.
